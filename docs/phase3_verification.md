## Real server persistence and recovery

A fresh demo-only server used the pinned official server image binaries under an isolated
WSL root filesystem, with its data bind-mounted from the ignored `.verification/phase3-demo-data`
directory. It listened only on loopback port 16379, with password authentication, AOF,
`appendfsync everysec`, RDB snapshots and `noeviction`. No secret was printed.

After replaying all scenarios, the backend was stopped and the server shut down with SAVE.
A new server process loaded its base RDB and incremental AOF successfully. A new backend
process then inspected the existing graph through the API **without seed or replay**.
All scenario snapshot counts, hashes, sequences, generations and the shared revision matched
the pre-restart verification oracle:

| B | 2 | 0 | 13 | `c28d74f2763925d6901b89dfb904cc1f1fa07cc29a26d0a77f46dd8c7cc34c2e` |

The local oracle is test output, never loaded by the application. This verifies a graceful
real database restart and backend process restart. It does not prove power-loss recovery;
`everysec` persistence can lose roughly the latest second of writes on abrupt host failure.

## Unverified environment and recovery limits

Docker Desktop's engine remains unavailable because of its existing Windows `dockerInference`
runtime socket failure. No system cleanup/reset was attempted during this phase. Docker image
builds, Compose network/volume behavior and container recreation could not be exercised.
Compose configuration can be validated locally; real FalkorDB behavior was verified with
official image binaries under WSL, not with a substitute database.

An older `.verification/data` AOF containing previous negative schema/test histories crashed
FalkorDB 4.22.1 during recovery in `GraphContext_GetSchemaByID`. Those files were retained.
The root cause was not established, and this report does not claim that failure was fixed.
The Compose test profile now runs negative tests against a separate, nonpersistent
`falkordb-test` server. Its malformed fixture histories cannot enter the persistent demo
server's recovery log. A fresh demo-only AOF recovered successfully as described above.
Recovery of arbitrary older test histories remains an upstream investigation item.

The IAM analysis is the documented synthetic subset, and agent observations are deterministic
fixtures. Full AWS policy semantics and live autonomous agents remain outside this phase.
